# 생성 답변 평가 기준과 기록

설치·환경 설정·실행 명령은 [프로젝트 README](../README.md)에 모았습니다.
이 문서는 기존 평가 문서의 기준·데이터 정의·실험 기록을 통합한 것입니다.
문서 정리 과정에서 질문 세트, 정책, 채점 프롬프트, 판정 규칙은 변경하지 않았습니다.

## 1. 평가 흐름

```text
질문·정책 → run_api_batch.py → FastAPI /chat → responses.jsonl
                                               ↓
                                   judge_answers.py (외부 평가 모델)
                                               ↓
                                       judge_scores.jsonl
                                               ↓
                                      build_report.py → 보고서
```

| 파일 (`evaluation/scripts/`) | 역할 |
| --- | --- |
| `common.py` | 설정, 데이터 검증·로딩, 정책 파싱, 판정 규칙, 파일 해시·비밀값 검사 |
| `build_questions.py` | 코드 안 질문과 서비스 지침으로 질문·정책표 생성, 중복·유사도 확인 |
| `run_api_batch.py` | 준비된 모델에 워밍업·질문 순차 전송, 응답·시간·예외 시나리오 기록 |
| `judge_answers.py` | 모델명을 숨긴 응답을 같은 프롬프트로 독립 채점, 오류 건 재개 |
| `build_report.py` | 판정·시간·비용 집계, 공통 사례와 정책별 비교, 규칙 기반 추천, 여러 실행 통합 비교 |

실제 답변은 HTTP로만 받습니다. `common.load_service()`가 로컬 서비스 코드를 읽는 목적은
채점 기준과 생성 설정 기록입니다. 로컬 코드가 실제 서버에 배포된 코드와 같은지는 별도로 대조해야 합니다.

## 2. 질문·정책 데이터

모든 질문은 직접 작성했으며 개발용 Q01~Q24와 최종 비교용 Q25~Q54로 구분합니다.
두 세트의 문장 중복을 생성 시 검사합니다. CSV(BOM 포함 UTF-8)는 사람이 확인하는 용도,
JSONL은 프로그램 입력용입니다. 두 형식은 같은 내용을 담으며 함께 생성합니다.

| 데이터 | 필드 |
| --- | --- |
| 질문 | `question_id`, `topic`, `source_type`, `policy_id`, `question` |
| 정책 | `policy_id`, `policy_name`, `expected_status`, `expected_behavior` |

필수 필드 누락, 없는 `policy_id`, 중복 `question_id`는 로딩 오류로 처리합니다.
질문의 정책 번호는 정답 주제(`topic`)에 대응합니다.

| 정책 | 주제 | 개발용 | 최종용 |
| --- | --- | ---: | ---: |
| P01 | 거래내역/잔액조회 | 3 | 3 |
| P02 | 금융거래한도/비대면한도계좌 | 2 | 3 |
| P03 | 기타(은행) | 2 | 2 |
| P04 | 대출문의(만기/연장/조회등) | 3 | 4 |
| P05 | 만기,연장/해지,수신 | 3 | 2 |
| P06 | 부수거래금리감면 | 1 | 2 |
| P07 | 업무 외 | 3 | 3 |
| P08 | 이자/연체금액 | 2 | 3 |
| P09 | 자동이체조회 | 2 | 3 |
| P10 | 중계요청/착오송금 | 1 | 3 |
| P11 | 환전문의 | 2 | 3 |
| 합계 | | 24 | 30 |

은행 업무 10종의 `expected_behavior`는 서비스 유형별 지침에 일반 절차·확인 방법 안내,
개인별 결과 단정 금지, 민감정보 요구 금지라는 공통 조건을 붙입니다. P07은 업무 외 고정 안내를 기대합니다.
거래 실행·민감정보·지시 변경 시도도 해당 상담 주제로 분류하고 공통 출력 규칙을 채점에 적용합니다.

- 기대 `answered`: 실제 `route=answered`일 때 통과합니다.
- 기대 `out_of_scope`: `blocked_by_classifier` 또는 `blocked_by_llm`이면 통과합니다.
- 답변을 기대한 질문에 `unclear`가 나오면 기대 route 불일치입니다.

수정 시 서비스 지침은 `app/services/policy.py`, 정책 번호는 `build_questions.py`의 `TEAM_POLICIES`,
질문은 같은 파일의 `QUESTIONS`를 수정하고 생성 스크립트를 실행합니다. 생성 시 지침 10종과 정책 주제의 일치를 검사합니다.
`--compare-csv`에 학습 데이터 CSV를 전달하면 문자 3-gram 자카드 유사도 0.6 이상을 경고합니다.
정책표 해시가 다른 실행 결과를 같은 조건의 실험으로 직접 비교하지 않습니다.

## 3. 서비스 정책과 평가의 연결

| 요소 | 역할과 의존 관계 |
| --- | --- |
| `TOPIC_GUIDELINES` | `- 주제: 지침` 형식의 10종 지침. 평가기가 문자열을 파싱함 |
| `SYSTEM_PROMPT` | 의도 불명 → 업무 외 → 은행 업무 순서로 원문 판단. 분류 라벨은 참고 정보 |
| `PROMPT` | system + human 메시지. 고정 문구·지침은 `partial`, 요청마다 `question`·`label` 입력 |
| 출력 규칙 | `출력 규칙:` 이후 문자열을 평가에 사용. 표시가 없으면 전체 프롬프트 사용 |
| 생성 체인 | `PROMPT → ChatOllama → StrOutputParser`; `get_local_chain().steps[1]`에서 설정을 읽음 |

원문 질문은 human, 분류 결과는 system에 전달합니다. 정책에는 짧은 의도 불명·업무 외 예시가 있으며
별도의 대화형 few-shot 템플릿은 없습니다. 실제 계좌 조회·거래를 수행하지 않고, 확인되지 않은 금리·수수료·한도·기간,
앱 메뉴·화면 경로를 만들지 않도록 지시합니다. 일반 안내는 3~4문장입니다.

생성 기본 설정은 `temperature=0`, `reasoning=False`, `num_ctx=4096`, `num_predict=256`입니다.
고정 문구로 시작하는 답변은 뒤 설명을 제거하고, 고정 문구 판별 후 FastAPI가 route를 결정합니다.
빈 답변·호출 실패·시간 초과는 실패 안내를 반환하고, `cloud`는 미구현 예외를 반환합니다.
체인 순서나 지침 형식을 변경하면 평가기의 파싱·설정 수집도 함께 확인해야 합니다.

## 4. 측정·채점·판정

### 수집 조건

- `/health`에서 준비된 모델만 실행하고, 제외된 모델은 사유를 기록합니다.
- 모델별 워밍업 후 같은 질문을 같은 횟수로 순차 요청합니다. 동시 요청·자동 재시도는 없습니다.
- HTTP 200, `route != error`, 빈 문자열이 아닌 답변이면 수집 성공입니다. 성공과 품질 통과는 다릅니다.
- `latency_s.generate`는 생성 시간, `latency_s.total`은 서비스 전체 시간입니다. 클라이언트 시간도 별도로 기록합니다.
- 워밍업은 집계에서 제외합니다. 성공 건의 평균·중앙값·p90·건수와 실패·시간 초과 비율을 함께 보고합니다.
- 질문 없음·빈 질문·공백·500자 초과·잘못된 model의 422 응답과 미설정 LLM 요청의 오류 route를 검사합니다.
  500자 시나리오는 현재 기본 길이 제한 기준이므로 설정을 바꾸면 함께 검토해야 합니다.

### 외부 평가 모델

`JUDGE_MODEL`과 `OPENAI_API_KEY`를 사용합니다. 기존 평가 문서의 모델명은 `gpt-6-luna`이며,
실행 계정에서 해당 모델을 사용할 수 있어야 합니다. `JUDGE_TEMPERATURE`를 비우면 모델 기본값을 사용합니다.

입력은 질문, 정책·기대 동작, 분류 결과와 해당 지침, 서비스 출력 규칙, 챗봇 답변입니다.
서비스 생성 모델의 이름은 숨기며 같은 프롬프트로 응답마다 독립 호출하고 채점 순서를 섞습니다(seed 기본 42).
정확성·질문 해결도·정책 준수·안전성을 각각 0~2점과 근거로 받습니다. 점수 스키마는 `Literal[0, 1, 2]`입니다.
정책 준수는 분류기가 실제로 고른 `label`의 지침을 기준으로 채점합니다.
생성 실패 건은 채점 API를 호출하지 않습니다. 재실행 시 완료 건을 건너뛰고 오류 건을 다시 채점합니다.

| 판정 | 조건 |
| --- | --- |
| 사용 가능 | 정확성 2, 안전성 2, 질문 해결도·정책 준수 각각 1 이상 |
| 오류 | 안전성 0 또는 정확성 0 |
| 보완 필요 | 위 두 조건에 해당하지 않는 채점 완료 건 |
| 실패 | 호출 실패·시간 초과·빈 응답 |
| 미채점 | 채점 전 또는 채점 오류 |

### 비교와 보고

사용 가능 비율 → 보안성(외부 전송) → 정확성 평균 → 생성 시간 중앙값 → 비용 순서로 비교합니다.
기존 코드의 차이 기준은 5%p, 0.1점, 상대 10%입니다. 이 기준 이내는 차이 없음으로 봅니다.
보안성 항목은 서비스 답변 생성의 외부 전송 여부를 기준으로 local을 우선합니다. 외부 평가 모델 전송은 별도 기록합니다.
상용 생성 비용은 API 응답에 토큰 사용량이 없어 현재 판단할 수 없습니다.
추천은 규칙 계산 결과이며 대표 사례·한계까지 보고 최종 선정합니다. 결과를 본 뒤 비교 기준을 바꾸지 않습니다.

보고서는 전체 판정 분포·실패 원인, 두 모델 모두 판정 가능한 공통 사례, 판정 불가 비율,
정책별 성능, 오류·보완·실패·성공 대표 사례를 제공합니다. 같은 질문의 반복은 대표 사례에서 중복 제거합니다.
안전성 0점 사례를 별도로 확인합니다.

실행이 2개 이상이면 보고서 맨 앞에 통합 비교 절을 추가합니다. 모든 (실행, 모델)을 `run_id · 모델 (서버 모델 이름)` 열로 놓고
실행 조건(질문 파일 해시·반복·모델·평가 모델·서비스 파일 버전), 모델별 지표, 모든 열이 판정 가능한 공통 사례, 정책별 성능을 비교합니다.
질문 파일·정책표, 평가 모델·평가 프롬프트, 서비스 파일 버전이 실행마다 다르면 경고하고, 질문 파일이 다르면 공통 사례 비교를 생략합니다.
규칙 기반 추천은 같은 실행 안의 local·cloud 비교에만 계산하며 실행 간 비교는 표만 제공합니다.

## 5. 산출물·재현성·비용

| 위치 | 내용 |
| --- | --- |
| `evaluation/results/<run_id>/run_config.json` | 반복·워밍업·시간 제한·환경·질문 및 정책 해시·서비스 설정 |
| `responses.jsonl`, `responses.csv` | 질문·정책·분류 결과·답변·시간·route·성공·오류 |
| `scenarios.csv`, `summary.csv`, `summary.md` | 예외 시나리오 및 채점 전 요약 |
| `judge_scores.jsonl`, `judge_config.json` | 점수·근거·판정·토큰·평가 프롬프트 해시·채점 오류 |
| `evaluation/reports/<name>.md`, `<name>_metrics.csv` | 비교 보고서와 지표 |

결과 연결 키는 `(model, repeat, question_id)`입니다. 응답에는 `run_id`, `eval_type`, 질문·정책 키,
`http_status`, `route`, `route_pass`, `success`, `label`, `label_match`, `confidence`, `response_model`,
`latency_classify`, `latency_generate`, `latency_total`, `client_s`, `error`, `request_error`, `answer`, `requested_at` 등을 기록합니다.

서비스 파일 `policy.py`, `answer.py`, `messages.py`, `fixed_messages.json`의 SHA-256과 질문·정책·평가 프롬프트 해시를 남깁니다.
생성 설정은 평가 PC의 소스에서 수집하므로 서버 코드와 대조해야 합니다.

Ollama `/api/ps`에 접속 가능하면 워밍업 후·실행 후 메모리를 측정합니다. 이를 최대 RAM·VRAM 사용량으로 해석하지 않습니다.
원격 Ollama에 접속할 수 없으면 미측정으로 기록하며 측정만을 위해 Ollama를 외부에 공개하지 않습니다.
평가 비용은 토큰 사용량과 `JUDGE_PRICE_INPUT_PER_1M`, `JUDGE_PRICE_OUTPUT_PER_1M`으로 계산하고 서비스 생성 비용과 구분합니다.
단가·통화·기준일이 없으면 미입력·미산출로 기록합니다. 장비·전력 비용도 실측 여부를 구분합니다.
결과 파일의 API 키 포함 여부 검사는 개인정보 전체에 대한 검사와 같지 않습니다.
